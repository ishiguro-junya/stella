# ドキュメントの書き方

`README.md`、`CONTRIBUTING.md`、`THIRD_PARTY_NOTICES.md`、`.agents/references/specifications/*.md`、`.agents/references/workflows/*.md`は、人が読むドキュメントとして日本語で書きます。  
`.agents/skills/*/SKILL.md`、`.agents/skills/*/agents/openai.yaml`、`.agents/references/roles/*.md`、`.codex/agents/*`、`.claude/agents/*.md`、`.cursor/agents/*.md`は、エージェント向けの定義と指示として英語で書きます。  
読み手が必要な情報へすぐにたどり着けることと、現在の実装に合っていることを優先します。  

## ドキュメントごとに書く内容を分ける

同じ説明を複数のドキュメントへ重ねず、次の責務に沿って書き分けます。  

| ドキュメント | 内容 |
| --- | --- |
| `README.md` | 導入、開発開始までの手順、ドキュメントへの入口 |
| `CONTRIBUTING.md` | 開発参加、変更の提出、貢献内容の権利条件 |
| `.agents/references/specifications/design.md` | 画面の視覚表現、共通操作、アクセシビリティ原則 |
| `THIRD_PARTY_NOTICES.md` | 配布物に含む第三者の著作物とライセンス |
| `.agents/references/specifications/product.md` | 利用者から見える動作、既定値、制約、対応範囲、対象外 |
| `.agents/references/specifications/architecture.md` | 内部境界、状態所有、処理ライフサイクル、実装上の不変条件 |
| `.agents/references/specifications/security.md` | 脅威モデル、信頼境界、安全性保証、機密情報、依存関係、例外方針 |
| `.agents/references/workflows/testing.md` | 変更に応じた検証方法 |
| `.agents/references/workflows/review.md` | 変更のレビュー方針と完了基準 |
| `.agents/references/workflows/release.md` | 配布手順 |
| `.agents/references/roles/*.md` | 役割エージェントの契約 |

別のドキュメントに詳しい説明がある場合は、内容を写さずリンクします。  
`README.md`のコマンド一覧には代表コマンドだけを載せ、`--smoke`などのオプション付きコマンドは[テスト](testing.md)と各コマンドの`--help`で説明します。  
コード変更によって仕様、利用方法、外部インターフェース、構築手順、運用手順が変わる場合は、関連するドキュメントを同じ変更内で更新します。  

## 新規ドキュメントを増やす前に既存ドキュメントへ統合する

原則として、新規のドキュメントファイルは作成しません。  
まず上の責務表から既存の統合先を選び、必要な内容だけを追記します。  
既存ドキュメントの責務に収まらず、継続して更新する独立した責務がある場合に限り、新規ファイルを作成します。  
一時的な検証結果や作業記録は恒久的なドキュメントにせず、コミットまたはプルリクエストの説明へ残します。  

## 一般名詞を英字のまま混在させない

一般名詞、状態、操作を表す語には、自然な日本語か、日本語として定着したカタカナ表記を使います。  
英字のまま残すのは、コード上の識別子、コマンド、パス、外部仕様で定められた名称、製品や規格の正式名称です。  
英字を残すか迷った場合は、その表記でなければ対象を特定できないかを基準にします。  

## プロダクト名と一般名詞を使い分ける

通常の説明ではプロダクト名「Stella」を主語にせず、「アプリ」と書くか主語を省略します。  
正式名称、見出し、コード上の識別子など、対象を特定するために必要な表記ではプロダクト名を使えます。  
一般名詞の「文書」は「ドキュメント」と書きます。  
この規則は、日本語で書く対象にだけ適用します。  

## 開発用コマンドの出力は英語で書く

`scripts/`配下のスクリプトと`wdio.conf.ts`が端末へ出力するメッセージは、英語で記述します。  

## 必要な情報から書く

ドキュメントや節の最初に、読み手が知りたい結論、目的、実行する操作を置きます。  
前置き、同じ内容の言い換え、根拠のない評価は加えません。  
因果関係や手順は地の文でつなぎ、互いに独立した項目だけを箇条書きや表にします。  

現在の実装だけを記述し、予定や過去の状態を現在の仕様と混ぜません。  
過去の合格結果、テスト件数、実行日時、ローカルの絶対パスはドキュメントへ残しません。  

## 一文ごとに改行する

日本語は句点、英語はピリオドなどの文末ごとに、一文を一行で書きます。  
Markdownでは、箇条書きを除く文章行の末尾に半角空白を2つ付けます。  
コードブロック、URL、バージョン番号、小数、略語、コード上の識別子に含まれるピリオドは文末として扱いません。  

## ドキュメントを変更したら検査する

ドキュメントを変更した場合は、次のコマンドを実行します。  

```sh
mise run lint:docs
```

このコマンドはMarkdownの書式、文章、リンクを検査します。  
コードや設定も変更した場合は`mise run lint`を実行します。  
プッシュ前は`mise run ci --smoke`から同じ検査が実行されます。
