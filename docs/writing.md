# ドキュメントの書き方

このリポジトリで人が読むドキュメントは、原則として日本語で書きます。  
読み手が必要な情報へすぐにたどり着けることと、現在の実装に合っていることを優先します。  

## ドキュメントごとに書く内容を分ける

同じ説明を複数のドキュメントへ重ねず、次の責務に沿って書き分けます。  

| ドキュメント | 内容 |
| --- | --- |
| `README.md` | 導入、開発開始までの手順、ドキュメントへの入口 |
| `CONTRIBUTING.md` | 開発参加、変更の提出、貢献内容の権利条件 |
| `DESIGN.md` | 画面の視覚表現と操作状態の規則 |
| `THIRD_PARTY_NOTICES.md` | 配布物に含む第三者の著作物とライセンス |
| `docs/specification.md` | 利用者から見える動作、制約、対応範囲 |
| `docs/architecture.md` | 内部構造、状態管理、永続化、安全性 |
| `docs/testing.md` | 変更に応じた検証方法 |
| `docs/release.md` | 配布手順 |

別のドキュメントに詳しい説明がある場合は、内容を写さずリンクします。  
コード変更によって仕様、利用方法、外部インターフェース、構築手順、運用手順が変わる場合は、関連するドキュメントを同じ変更内で更新します。  

## 新規ドキュメントを増やす前に既存ドキュメントへ統合する

原則として、新規のドキュメントファイルは作成しません。  
まず上の責務表から既存の統合先を選び、必要な内容だけを追記します。  
既存ドキュメントの責務に収まらず、継続して更新する独立した責務がある場合に限り、新規ファイルを作成します。  
一時的な検証結果や作業記録は恒久的なドキュメントにせず、コミットまたはプルリクエストの説明へ残します。  

## 一般名詞を英字のまま混在させない

一般名詞、状態、操作を表す語には、自然な日本語か、日本語として定着したカタカナ表記を使います。  
英字のまま残すのは、コード上の識別子、コマンド、パス、外部仕様で定められた名称、製品や規格の正式名称です。  
英字を残すか迷った場合は、その表記でなければ対象を特定できないかを基準にします。  

## プロダクト名と一般名詞を使い分ける

通常の説明ではプロダクト名「Stella」を主語にせず、「アプリ」と書くか主語を省略します。  
正式名称、見出し、コード上の識別子など、対象を特定するために必要な表記ではプロダクト名を使えます。  
一般名詞の「文書」は「ドキュメント」と書きます。  
この規則は、`.agents/skills/`配下のスキルに含まれる人が読む文章にも適用します。  

## 開発用コマンドの出力は英語で書く

`scripts/`配下のスクリプトと`wdio.conf.ts`が端末へ出力するメッセージは、英語で記述します。  

## 必要な情報から書く

ドキュメントや節の最初に、読み手が知りたい結論、目的、実行する操作を置きます。  
前置き、同じ内容の言い換え、根拠のない評価は加えません。  
因果関係や手順は地の文でつなぎ、互いに独立した項目だけを箇条書きや表にします。  

現在の実装だけを記述し、予定や過去の状態を現在の仕様と混ぜません。  
過去の合格結果、テスト件数、実行日時、ローカルの絶対パスはドキュメントへ残しません。  

## 一文ごとに改行する

日本語は句点、英語はピリオドなどの文末ごとに、一文を一行で書きます。  
Markdownでは、箇条書きを除く文章行の末尾に半角空白を2つ付けます。  
コードブロック、URL、バージョン番号、小数、略語、コード上の識別子に含まれるピリオドは文末として扱いません。  

## ドキュメントを変更したら検査する

ドキュメントを変更した場合は、次のコマンドを実行します。  

```sh
mise run lint
```

このコマンドはコードや設定と併せて、Markdownの書式、文章、リンクを検査します。  
プッシュ前にも同じ検査が実行されます。
